        Architecture overview
        

          
Eight roles are available to the studio; this run activated the ones the workflow actually needed:

          
    
            
  • Planner — turns the free-text spec into a function contract, signature, and a concrete test plan (happy path, edge cases, invalid input). Runs once, before round 1.
    • 
            
  • Executor — writes the first draft: the implementation and a pytest suite following the Planner's contract.
    • 
            
  • Evaluator — re-scores the current draft every round against the rubric (quality, correctness, edge-case handling), on a fresh 0–10 scale, with a structured breakdown.
    • 
            
  • Critic — takes the Evaluator's score and independently argues what's still wrong, in prose a human reviewer would recognize.
    • 
            
  • Safety Monitor — scans each draft for dangerous patterns (eval, exec, os.system, unchecked file/network I/O) — advisory, does not block the loop unless something is actually flagged.
    • 
            
  • Improver — rewrites the draft using that round's evaluation + critique as its brief. Its output becomes next round's draft.
    • 
            
  • Memory Manager — after each round, condenses what changed and why into a short persistent note, so the Improver isn't re-explaining the same fix two rounds later.
    • 
            
  • Final Reviewer — runs once, after a stop condition fires, and writes the sign-off summary shown above.
    • 
          

          
How the stop-check governs the loop: every round, after Evaluator + Critic + Safety Monitor return, the orchestrator checks three conditions in order — plateau (score improved by less than 0.3 for two consecutive rounds), threshold (score has crossed the target set at intake), and a hard iteration cap (a safety fallback, not the intended ending). The first one that's true ends the loop and routes to the Final Reviewer instead of another Improver pass. This is why the round counter never shows "of N" — the runtime doesn't know how many rounds it'll take until a check actually fires.
        

      


      

        Extension ideas
        

          
    
            
  • Add a real sandboxed pytest execution step (e.g. Pyodide in-browser) so the Evaluator scores against actual pass/fail output instead of static reading.
    • 
            
  • Let the Critic and Evaluator run as two independent API calls in parallel each round, then have a lightweight arbiter reconcile disagreement before the Improver sees either.
    • 
            
  • Persist Memory Manager notes across separate specs, so recurring mistakes (e.g. "always forgets empty-list edge case") get baked into the Planner's contract from round 0.
    • 
            
  • Swap the stopping rule for a cost-aware one: stop early if projected score gain per additional API call drops below a threshold.
    • 
            
  • Add a human-in-the-loop gate: pause after any round where the Critic and Evaluator scores diverge by more than 2 points.
    •
