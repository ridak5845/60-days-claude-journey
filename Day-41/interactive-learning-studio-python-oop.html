Module 1 · Foundations

Classes, Objects & Attributes

The vocabulary and mental model every OOP concept is built on: what a class actually is, how objects come to life, and how they hold their own data.

Explanation

In Python, everything is an object — numbers, strings, functions, even classes themselves. A class is a blueprint that describes what data (attributes) and behavior (methods) its objects will have. An object (or instance) is a concrete thing built from that blueprint, living in memory with its own copy of the data.

You define a class with the class keyword. Inside it, the special method __init__ runs automatically every time a new object is created — it's the constructor, responsible for setting up that object's starting state. The first parameter of every instance method, by convention named self, refers to the specific object the method was called on.

class Dog: # class attribute — shared by all instances species = "Canis familiaris" def __init__(self, name, age): # instance attributes — unique per object self.name = name self.age = age def bark(self): return f"{self.name} says woof!" rex = Dog("Rex", 3) bella = Dog("Bella", 5) print(rex.bark()) # Rex says woof! print(bella.age) # 5 print(rex.species) # Canis familiaris (shared)

Notice: rex and bella are two separate objects. Each has its own name and age, but both share the same species class attribute — because it belongs to the class, not to any one instance.

Analogy

Think of it like...
A class is an architectural blueprint for a house — it specifies "every house has walls, a door, and a roof" but is not itself a house you can live in. Each object is an actual house built from that blueprint. You can paint one house blue and another red (instance attributes) without changing the blueprint, but if the blueprint says "3 bedrooms," every house built from it starts with that layout.

Common Misconceptions

Misconception
"self is a Python keyword." It isn't — it's just a naming convention. Python passes the instance as the first argument to every instance method automatically; you could call it anything, but every Python developer expects self, so deviating from it makes code harder to read.
Misconception
"Class attributes and instance attributes with the same name are the same variable." They're not. Assigning self.age = 5 inside a method creates (or overwrites) an instance attribute that shadows a class attribute of the same name — the class attribute underneath is untouched.

Key Takeaways

  • A class is a blueprint; an object (instance) is a concrete thing built from it.
  • __init__ runs automatically on creation and sets up initial state via self.
  • Instance attributes belong to one object; class attributes are shared by all objects of that class.
  • Methods are just functions defined inside a class that automatically receive the calling object as self.
Module 2 · Core Pillars

Encapsulation, Inheritance, Polymorphism, Abstraction

The four ideas that make OOP more than "functions bundled with data" — and the concrete Python syntax for each.

Explanation

Encapsulation means bundling data with the methods that operate on it, and controlling access to that data. Python has no true "private" enforcement, but uses naming conventions: a single underscore (_balance) signals "internal, don't touch directly," and a double underscore (__balance) triggers name-mangling to discourage accidental access from subclasses.

class BankAccount: def __init__(self, balance): self._balance = balance # "protected" by convention def deposit(self, amount): if amount > 0: self._balance += amount def get_balance(self): return self._balance

Inheritance lets a class (subclass) reuse and extend the behavior of another class (superclass), avoiding duplication.

class Animal: def __init__(self, name): self.name = name def speak(self): return "..." class Cat(Animal): # Cat inherits from Animal def speak(self): # overrides parent's speak() return f"{self.name} says Meow"

Polymorphism means objects of different classes can be used through the same interface — calling .speak() works the same way regardless of the exact subclass, and each responds in its own way.

class Dog(Animal): def speak(self): return f"{self.name} says Woof" for pet in [Cat("Tom"), Dog("Rex")]: print(pet.speak()) # each animal responds differently

Abstraction hides internal complexity behind a simple interface. Python formalizes this with abc.ABC and @abstractmethod, forcing subclasses to implement certain methods before they can be instantiated.

from abc import ABC, abstractmethod class Shape(ABC): @abstractmethod def area(self): ... # no implementation — subclasses must provide one

Analogy

Think of it like...
A TV remote is encapsulation — you press "volume up" without knowing the internal circuitry. A "vehicle" blueprint that "car" and "motorcycle" both build on is inheritance. Every vehicle having a drive() method that behaves differently per vehicle type is polymorphism. And a "Payment Method" interface that just says "must have a pay() method" without saying how, is abstraction — it defines the contract, not the implementation.

Common Misconceptions

Misconception
"Double underscore attributes (__balance) are truly private, like in Java." They aren't — Python performs name mangling (renaming to _ClassName__balance), which makes accidental access harder but not impossible. Python's privacy is a convention, enforced by discipline, not the interpreter.
Misconception
"Polymorphism requires inheritance." In Python it often doesn't — duck typing means any object with a matching method works, regardless of its class hierarchy: "if it walks like a duck and quacks like a duck..."

Key Takeaways

  • Encapsulation in Python is convention-based (_, __), not strictly enforced.
  • Inheritance lets subclasses reuse and override parent behavior.
  • Polymorphism means the same method call can behave differently depending on the object's actual type.
  • Abstraction defines a required contract via ABC + @abstractmethod, deferring implementation to subclasses.
Module 3 · Practical Application

Properties, Dunder Methods & Composition

The idioms that separate "code that uses classes" from Pythonic, professional object design.

Explanation

Class methods (@classmethod) receive the class itself (cls) rather than an instance — commonly used for alternative constructors. Static methods (@staticmethod) receive neither self nor cls — they're utility functions that logically belong inside the class namespace.

class Pizza: def __init__(self, toppings): self.toppings = toppings @classmethod def margherita(cls): # alternative constructor return cls(["tomato", "basil"]) @staticmethod def is_valid_topping(name): # no self/cls needed return name.islower()

Properties (@property) let a method be accessed like an attribute — useful for computed values or validated setters without breaking the simple obj.attr syntax.

class Circle: def __init__(self, radius): self._radius = radius @property def area(self): return 3.14159 * self._radius ** 2 c = Circle(4) print(c.area) # called like an attribute, no parentheses

Dunder methods ("double underscore") let your objects integrate with Python's built-in syntax — +, len(), print(), equality checks, and more.

class Vector: def __init__(self, x, y): self.x, self.y = x, y def __add__(self, other): return Vector(self.x + other.x, self.y + other.y) def __repr__(self): return f"Vector({self.x}, {self.y})" print(Vector(1,2) + Vector(3,4)) # Vector(4, 6)

Composition builds complex objects out of simpler ones ("has-a") instead of inheriting from them ("is-a"). A Car has an Engine — it doesn't make sense for Car to inherit from Engine.

class Engine: def start(self): return "Vroom" class Car: def __init__(self): self.engine = Engine() # Car HAS-A Engine def start(self): return self.engine.start()

Analogy

Think of it like...
A @classmethod alternative constructor is like ordering "the usual" at a café — a shortcut recipe for building the same drink a different way. A @property is a vending machine slot labeled "Price" that actually computes the price live rather than storing a fixed number. And composition vs. inheritance is "a car has an engine" vs. "a car is a kind of engine" — the second sentence is obviously wrong, which is exactly the smell that tells you composition is the right choice.

Give Circle a @property called radius with a setter that raises ValueError if the value is negative.

class Circle: def __init__(self, radius): self.radius = radius # goes through the setter below @property def radius(self): return self._radius @radius.setter def radius(self, value): if value < 0: raise ValueError("radius can't be negative") self._radius = value

Common Misconceptions

Misconception
"@staticmethod and @classmethod are interchangeable." They're not — a staticmethod can't access the class or instance at all, while a classmethod always has cls and can create new instances or read class attributes.
Misconception
"Inheritance is always better than composition because it's 'more OOP'." Overusing inheritance creates rigid, deeply nested hierarchies that are hard to change. The rule of thumb "favor composition over inheritance" exists because "has-a" relationships are usually more flexible than "is-a" ones.

Key Takeaways

  • @classmethod gets cls and is often used for alternative constructors.
  • @staticmethod gets neither self nor cls — it's a plain function living in the class.
  • @property lets computed or validated values be accessed like plain attributes.
  • Dunder methods hook your objects into Python's built-in operators and functions.
  • Composition ("has-a") is often more flexible than inheritance ("is-a") for combining behavior.
Module 4 · Mastery

Multiple Inheritance, MRO & Design Judgment

The advanced mechanics — and the design judgment — that separate someone who knows OOP syntax from someone who designs good class hierarchies.

Explanation

Python supports multiple inheritance — a class can inherit from more than one parent. When two parents define the same method, Python needs a deterministic rule for which one wins: the Method Resolution Order (MRO), computed with the C3 linearization algorithm. You can inspect it directly with ClassName.__mro__ or ClassName.mro().

class Flyer: def move(self): return "Flies" class Swimmer: def move(self): return "Swims" class Duck(Flyer, Swimmer): # multiple inheritance pass print(Duck().move()) # "Flies" — Flyer is checked first (left-to-right) print(Duck.__mro__) # (Duck, Flyer, Swimmer, object)

super() uses the MRO to call the next method in line — critical in multiple inheritance so every parent's __init__ gets a chance to run, instead of hardcoding a specific parent class name.

class Base: def __init__(self): print("Base init") class Child(Base): def __init__(self): super().__init__() # delegates up the MRO chain print("Child init")

Deep or wide multiple-inheritance hierarchies are a common source of bugs and confusion. Mixins — small classes meant only to add one piece of reusable behavior, never instantiated on their own — are the disciplined way to use multiple inheritance without the mess. Common design patterns built on OOP fundamentals include the Factory pattern (a classmethod or function that returns different subclass instances) and the Strategy pattern (swap in different behavior objects via composition).

Analogy

Think of it like...
MRO is like a company's escalation chain: when you have a question your immediate manager can't answer, there's a defined, predictable order of who gets asked next — never ambiguous, always the same path. Mixins are like adding a single specialized skill badge to an employee (e.g., "certified forklift operator") — useful attached to a role, but meaningless as a standalone job title on its own.

Practical Exercise

Try it yourself

Design a small Notifier system: a Notifier base class with an abstract send(message), plus EmailNotifier and SMSNotifier subclasses (Strategy pattern). Sketch the class signatures.

class Notifier(ABC): @abstractmethod def send(self, message): ... class EmailNotifier(Notifier): def send(self, message): return f"Emailing: {message}" class SMSNotifier(Notifier): def send(self, message): return f"Texting: {message}" # usage swaps strategy at runtime: def alert(notifier: Notifier, msg): return notifier.send(msg)

Common Misconceptions

Misconception
"super().__init__() always calls the immediate parent class." It actually calls the next class in the MRO — in multiple inheritance, that may not be the class you expect, which is exactly why relying on MRO-aware super() calls (instead of naming a parent explicitly) matters.
Misconception
"More inheritance levels = better design." Deep hierarchies are usually a sign of over-engineering. Experienced developers reach for composition and mixins first, and use deep inheritance chains sparingly.

Key Takeaways

  • MRO defines a deterministic order for resolving methods in multiple inheritance; inspect it with __mro__.
  • super() follows the MRO, not a hardcoded parent — essential for cooperative multiple inheritance.
  • Mixins add one reusable capability and are never meant to stand alone.
  • Favor composition and shallow hierarchies; reach for deep inheritance only when a genuine "is-a" relationship exists.

Final Practical Challenge

Build a small Library Management system. Design classes that satisfy all of the following:

  • A Media abstract base class with an abstract info() method (abstraction).
  • Book and DVD subclasses that inherit from Media and override info() differently (inheritance + polymorphism).
  • A _copies_available attribute protected by convention, exposed via a @property, with checkout()/return_item() methods that validate before mutating it (encapsulation).
  • A Library class that has a list of Media objects — not inherits from them (composition).
  • A @classmethod on Book called from_isbn_lookup(cls, isbn) as an alternative constructor.
from abc import ABC, abstractmethod class Media(ABC): def __init__(self, title, copies): self.title = title self._copies_available = copies @property def copies_available(self): return self._copies_available def checkout(self): if self._copies_available <= 0: raise ValueError("No copies available") self._copies_available -= 1 def return_item(self): self._copies_available += 1 @abstractmethod def info(self): ... class Book(Media): def __init__(self, title, copies, author): super().__init__(title, copies) self.author = author def info(self): return f"{self.title} by {self.author}" @classmethod def from_isbn_lookup(cls, isbn): # pretend lookup return cls(f"Book #{isbn}", 1, "Unknown") class DVD(Media): def info(self): return f"{self.title} (DVD)" class Library: def __init__(self): self.catalog = [] # Library HAS-A list of Media def add(self, item): self.catalog.append(item)

  • Classes are blueprints; objects are instances with their own state.
